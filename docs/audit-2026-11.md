# Rhino Studio pre-release audit, November 2026

Audited on 2026-11-11 against Rhino Studio `bbd25ac` (0.24.1) and Tool Manager `ed0f20f` (1.9.28), both clean on
`main`. Standard: the safety model in both `AGENTS.md` files, `docs/decisions.md` and `docs/invariants.md`.
No code was changed. Tests run on this PC: Studio `npm test` 888/888 pass, `npm run build` clean (two chunks over
500 kB, see N4); Tool Manager `dev/run_all.sh` every suite passed, with the three expected skips (updater run needs
root, real Klipper needs `KLIPPER_DIR`).

Where a finding depends on how Klipper or Moonraker parse things, it was checked against their source: Klipper
`klippy/gcode.py` (`args_r`, `_process_commands`, `_get_extended_params`) and Moonraker `components/application.py`
and `components/authorization.py`, current `master` on 2026-11-11.

**Status, same day:** M1-M5 fixed in Rhino Studio 0.25.0 and Tool Manager 1.9.29 (not yet pushed): M1-M3 in
`commands.ts` with tests; M4 as `rhino/portal/hosts.py` checked by `security.check_write`; M5 as ed25519-signed
releases (`scripts/rhino_update_helper.py`, `dev/sign_release.py`, `release.yml`) plus the README rewrite. U1 is
on-machine check SEC1 in `docs/testing.md`. The Should-fix list is untouched.

## 1. Summary

The safety model is real: every Moonraker and Portal request goes through an allowlist, tool state only ever comes
from Klipper, the machine-side macros enforce the heater and homing rules again, and the updater, network helper and
backups are designed so the Portal never holds root. The console classifier, which is the one gate every typed
command passes, has three gaps that let a one-line command skip its confirmation (a leading `N1`, the `.1`
`rename_existing` targets such as `G28.1`, and quoted parameter values). On the network side the Portal's write
protection falls to DNS rebinding, and from there any release-shaped zip is installed as root. Fix those five first
(M1-M5); the rest is polish a critic would mention but that cannot hurt a machine.

## 2. Must fix before public alpha

### M1. Line-numbered commands skip the classifier
- `rhino-studio/src/control/commands.ts:120-125` (`commandOf`), Klipper `klippy/gcode.py:211`.
- Klipper drops a leading `N<number>` before reading the command; Studio does not. `N1 G28` is classified as the
  command `N1`, risk `none`, and goes out with no confirmation.
- Scenario: a user types `N1 M3 S255` or `N1 FORCE_MOVE STEPPER=stepper_z DISTANCE=50 VELOCITY=50` on Control's
  console. No dialog. The laser powers or the bed moves 50 mm with no limits. Checked by reproducing Klipper's parse:
  `'N1 G28' -> 'G28'`, `'n7 force_move ...' -> 'FORCE_MOVE'`.
- Fix: in `commandOf`, strip `^[Nn]\d+\s*` before anything else, and add the cases to `commands.test.ts`. Small.

### M2. `rename_existing` targets (`G28.1`, `M104.1`, `M109.1`, `G1.1`, `G0.1`) are unclassified
- `rhino-studio/src/control/commands.ts:122` keeps the whole `G28.1` as the command; `MOTION` only knows `G28`.
  Wrappers: `Toolhead_Manager/toolchanger.cfg:277, 286, 295, 330`, `tools/3dp_macros.cfg:175, 207`.
- The Rhino's `G28` wrapper refuses to home Z without a print head because "the probe is on the print heads, so
  homing Z now would drive the bed into the tool" (`toolchanger.cfg:345`). `G28.1` is the raw Klipper homing it wraps.
  Studio classifies `G28.1` as risk `none`: no confirmation, and the machine-side guard is skipped too. `M104.1 S250`
  heats the hotend with a laser mounted, past both the UI rule (`control.ts:297`) and the `_RHINO_HEAT_OK` wrapper.
- Scenario: LightSaber mounted; a user who saw `G28.1` in the command list (Studio loads `printer.gcode.help`,
  `machine.ts:76`) types `G28.1 Z`. The bed rises with no probe to stop it.
- Fix: classify `X.n` as its base command (`G28.1` → the `G28` entry) with the reason "…and skips the Rhino's own
  check", or refuse `.1` forms outright (they exist only as wrapper targets). `_SET_HEATER_TEMPERATURE_BASE` is
  already caught by the `_` rule. Tests. Small.

### M3. Quoted parameter values bypass the tool-state rules
- `rhino-studio/src/control/commands.ts:148-151`. Klipper reads extended parameters with `shlex`
  (`_get_extended_params`), so `MACRO="SWAP_TOOL"` and `MACRO=SWAP_TOOL` are the same command. Studio's regexes
  `MACRO\s*=\s*SWAP_TOOL` and `VARIABLE\s*=\s*current_tool\b` do not match the quoted form.
- Scenario: `SET_GCODE_VARIABLE MACRO="SWAP_TOOL" VARIABLE=current_tool VALUE=1` goes out as risk `none`. Klipper
  now believes BlockOne is mounted; every "needs a confirmed print head" gate (homing Z, heating, jogging) opens
  while the laser is on the carriage. `SAVE_VARIABLE VARIABLE="current_tool" VALUE=1` does the same to the saved slot.
- Fix: use the existing `param()` helper (it handles quotes) for `MACRO`, `VARIABLE` and `MOVE`, and test the quoted
  forms. Small.

### M4. DNS rebinding reaches the Portal's writes
- `Toolhead_Manager/rhino/portal/security.py:24-31` (Origin must equal `request.host`),
  `service/rhino-studio.nginx:113-117` (`Host $http_host` is passed through, `server_name _`),
  `rhino/portal/routes.py:85` (the write token is in the home page), `install.sh:544` (the port-80 site is
  `default_server`, any name).
- The Origin check compares the browser's `Origin` with the `Host` header the browser sent. Under DNS rebinding both
  are the attacker's name, so they match; the token is then readable with a same-origin `GET /portal/`.
- Scenario: someone on the home network opens a malicious page. The page's name is rebound to the Rhino's address, it
  reads the token, then POSTs `/api/update/upload` with a crafted zip and `/api/update/install`. The root updater
  installs it (see M5). Other writes reachable the same way: full restore, Wi-Fi and address changes, trusted_clients.
- What Mainsail shares: Moonraker makes no Host check either (verified in `application.py` /
  `authorization.py`: an Origin outside `cors_domains` gets no CORS headers but the request is still served), so a
  rebound page can already run G-code and edit `printer.cfg` as the `pi` user on any Mainsail machine. Studio adds
  the step to root.
- Fix: the Portal refuses every `/api` request whose `Host` (without port) is not one of: the machine's hostname,
  `<hostname>.local`, `rhinostudio.local`, `localhost`, or an IP literal. Optionally the nginx default server does
  the same (`if ($host !~ …) { return 444; }`), keeping IP literals and `.local` names. Small to medium.

### M5. Any release-shaped zip is installed as root, and the README says the opposite
- `Toolhead_Manager/scripts/rhino_update_helper.py:54-95` (`check_zip`: names, sizes, a `VERSION` file),
  `:247-259` (runs the zip's own `install.sh` as root), `rhino/portal/update_routes.py:281-303` (upload path),
  `README.md:127-131` ("it can't run G-code or restart mid-print").
- The upload path checks shape, not origin. There is no signature; the GitHub path checks a `.sha256` that sits
  beside the zip in the same release, which proves the download arrived intact, not that it came from Mike.
- Scenario: anyone Moonraker trusts (every device on the LAN by default, every device on the tailnet if that range
  is added, or a rebound page per M4) uploads a zip whose `install.sh` adds a user with sudo. `rhino-update.path`
  starts the helper, which runs it as root.
- Honest comparison: a stock Mainsail host already lets the LAN edit `moonraker.conf` and run shell commands as `pi`,
  who usually has sudo; Studio makes it one request and root outright. The README's security paragraph predates the
  updater, restore and network changes and is now wrong.
- Fix: (a) sign releases: `release.yml` signs the zip with a minisign/ed25519 key, the public key is embedded in
  `rhino_update_helper.py`, and both `check_zip` callers require a valid signature (keep "install an unsigned zip"
  for the SSH menu only, with a typed confirmation); (b) rewrite README › Security to say what the Portal can do today
  and that trusted_clients is the only gate. Medium.

## 3. Should fix

### S1. Macros that wrap motion or heat run with no confirmation
- `rhino-studio/src/control/commands.ts:183-184` (any name not in the lists is `none`),
  `src/control/userMacros.ts:271-273` (the "Run a macro" step), `src/control/MacroPanel.vue:73-81`.
- The classifier knows the Rhino's macro names, not what a user's own macro does. `MY_PARK` containing `G28` and
  `G1 Z200` is a plain button press. The design note calls this a guard against slips, which is fair, but the
  macro definitions are already fetched (`client.ts:339 macroDefinitions`) and could be scanned.
- Scenario: a user adds `[gcode_macro WARM] gcode: M104 S240` to `printer.cfg`, then presses it with the knife mounted.
  The machine-side `M104` wrapper refuses, so nothing heats on the Rhino; on another person's machine without those
  wrappers it heats.
- Fix: when a line's command is a `gcode_macro`, classify by the worst MOTION/POWER/RESTART word found in its
  `gcode` text (Jinja and all; false positives only add a dialog). Medium.

### S2. Prompt buttons written by a job file run unchecked
- `rhino-studio/src/control/prompts.ts:33-37`, `src/control/commands.ts:232-237` (`fromPrompt` sends as-is),
  `src/slicer/check.ts:46-54` (`FORBIDDEN` has no `RESPOND … action:prompt` entry).
- Prompts are trusted because a macro wrote them, but any G-code file can emit `RESPOND TYPE=command
  MSG="action:prompt_button Continue|FORCE_MOVE …|primary"`. Studio shows "needs you" on the Dashboard and the
  button on Control; the command's only exposure is a tooltip (`PromptDialog.vue:33`). Mainsail behaves the same.
- Fix: `check.ts` marks `action:prompt` lines in prepared and uploaded files as an error; `pressPromptButton` runs
  the command through `check()` and refuses the `NEVER` list, showing the command under the label. Small.

### S3. Studio can be framed (clickjacking)
- `Toolhead_Manager/service/rhino-studio.nginx` sets no `X-Frame-Options` or `frame-ancestors` for Studio's pages;
  only the Portal's own responses carry `frame-ancestors 'none'` (`security.py:20`).
- Scenario: a page frames `http://rhino.local/#/control` invisibly and positions a "Click to win" button over the
  padlock and a jog arrow, or over a confirmation's OK. Needs the LAN, like everything else here.
- Fix: `add_header X-Frame-Options "DENY" always;` and a `Content-Security-Policy "frame-ancestors 'none'"` in the
  site file. Small.

### S4. Heater limits are hard-coded, and don't match the config
- `rhino-studio/src/control/commands.ts:276` (300/130), `src/slicer/check.ts:71` (`HEAT_MAX`),
  `src/control/userMacros.ts:46-47`; the machine has `max_temp: 290` (`tools/3dp.cfg:35`).
- A user types 295 on Control: Studio accepts it, Klipper answers "out of range (…:290.0)" and the console shows
  that raw error. On another machine with `max_temp: 260` the same happens at 261.
- Fix: read `configfile.settings.extruder.max_temp` and `heater_bed.max_temp` once (the `extruderConfig()` read
  already exists) and use them everywhere the limits appear; keep 300/130 only as the ceiling. Small.

### S5. The Hardware and Tuning padlocks never time out
- `rhino-studio/src/stores/control.ts:334-343` (`tuneUnlocked`), `:362-367` (`hwUnlocked`). Motion (`:235-237`) and
  the lead screws (`:421-427`) relock after 60 s and when the page is hidden; these two relock only on unmount,
  tool change, job start and Klipper not ready.
- Scenario: Hardware unlocked on a phone to switch a coolant pump; the phone goes in a pocket. Twenty minutes later
  the page is still unlocked and a pocket tap toggles a live relay. `AGENTS.md` lists the four relock cases these
  meet, so this is a gap against the audit's list, not the written rule.
- Fix: one shared `timedLock(UNLOCK_MS)` helper for all four padlocks, with the `visibilitychange` listener. Small.

### S6. Tool Manager has no LICENSE file
- `Toolhead_Manager/` root: no `LICENSE`; `git ls-files` finds none. Studio has GPL-3.0 (`rhino-studio/LICENSE`),
  and `client_mainsail.cfg` is a GPL-3.0 copy, so the repo must be GPL-3.0-compatible anyway.
- A public repo with no licence file is "all rights reserved" by default; it's the first thing a critic checks.
- Fix: add `LICENSE` (GPL-3.0-or-later to match Studio) and a one-line Licence section in the README. Small.

### S7. Both READMEs describe an older install
- `rhino-studio/README.md:131-139`: Studio "on a port of its own: `http://<pi>:5001`", "Mainsail's site isn't
  touched". Since 1.9.19 Studio answers the bare address and Mainsail moves to 8090 (`decisions.md` 2026-11-09).
  `Toolhead_Manager/README.md:81-111`: Quick start uploads the zip "in Mainsail", prints "from Mainsail", calls the
  host "the Pi" though releases target the 7050 (x86).
- Fix: rewrite both install sections from the manual's *Install and first start* chapter. Small.

### S8. `Prompt.md` in the Tool Manager root is a stale, contradictory spec
- `Toolhead_Manager/Prompt.md:1-5`: "MASTER SPECIFICATION… 5-axis hybrid… OrcaSlicer frontend", emoji headings.
  It contradicts README and `AGENTS.md` and reads like an AI prompt left in a public repo.
- Fix: delete it, or move the still-true parts into `docs/` under a dated name. Small.

### S9. Test coverage gaps on the safety-critical files
- `rhino-studio/src/stores/control.ts` (every padlock, `send()`'s confirm gate, the heater rule) and
  `src/stores/machine.ts` have no `*.test.ts`. `commands.test.ts` has no case for `N1 …`, `G28.1`, or quoted
  parameters (M1-M3). `invariants.md` A2 notes nothing asserts that only `approve`/`fromPrompt` make a
  `CheckedScript`.
- Fix: a Pinia test for the control store (unlock → block → relocked; hotend refused without DEPOSITION), the three
  classifier cases, and a source-grep test that `as CheckedScript` appears only in `commands.ts`. Small to medium.

### S10. Example addresses look like the real home network
- `Toolhead_Manager/rhino/trust.py:38` (`192.168.86.31/24` in a docstring), `dev/test_trust.py:58-62`,
  `scripts/rhino_net_helper.py:93`. Not secrets, but a critic will say "that's his LAN".
- Fix: use `192.0.2.0/24` (RFC 5737) in docstrings and tests. Small.

## 4. Nitpicks

- N1. `rhino-studio/README.md:231-239` licence table names two fonts; `package.json` ships sixteen Fontsource
  families (Anton, Bebas Neue, Orbitron, Righteous, …). All are OFL on Google Fonts, so one line "every Fontsource
  font, OFL 1.1" settles it. Small.
- N2. `Toolhead_Manager/manual/Rhino-User-Manual.pdf` (29.8 MB) is tracked in git and rebuilt each release, so every
  clone carries every version. The roadmap already lists PDF size; moving it to a release asset would cut the repo
  more than shrinking it. Small.
- N3. `service/rhino-studio.nginx:23` `client_max_body_size 0` on the whole site (Mainsail does the same for
  uploads); a `location /websocket` and `/portal/` limit already exist, so the Studio root could keep a limit too.
  Small.
- N4. `npm run build`: `rhino3d` 594 kB and `FileEditor` 325 kB chunks. Both are lazy-loaded, so this only costs on
  the first Dashboard open over slow Wi-Fi; worth a note in the README's "weak hardware" paragraph. Small.
- N5. The updater's failure text (`rhino_update_helper.py:263`) says "Undo with rhino.sh option 4" and not that
  Studio's own "Go back" also works while Klipper is down (`update_routes.py:323` lets the request through when
  Moonraker answers "unknown"). Say both. Small.

## 5. Unconfirmed

- U1. **Moonraker trusts `X-Real-IP` from any client.** `application.py` passes `xheaders=self.use_xheaders`
  (default `True`) to Tornado and `authorization.py` checks `request.remote_ip`, which Tornado takes from
  `X-Real-IP` / `X-Forwarded-For` when `xheaders` is on; the Portal's own trust check relies on exactly this
  (`rhino/moonraker.py:504-507`). If so, `curl -H 'X-Real-IP: 127.0.0.1' http://<rhino>:7125/access/info` from an
  address not in `trusted_clients` answers as trusted, and port 7125 must be kept off any untrusted network. This is
  Moonraker's behaviour and Mainsail's exposure, not Studio's, but the Trusted addresses screen implies more
  protection than that. Settle it with that one curl from a laptop that isn't trusted.
- U2. **Rebinding against Moonraker over the websocket.** Verified in source that Moonraker makes no Host check; not
  exercised. Settle with a rebinding test page against a spare host.
- U3. **Pi 3B / J1800 load with the hologram plus a camera stream.** Nothing here measures it; the roadmap already
  says test on the kiosk.

## 6. Already solid

- **Allowlists with tests.** `READ_ONLY_METHODS`, `ACTION_METHODS`, `FILE_METHODS` with root checks, and
  `WRITE_ROUTES` (one method and path regex per write kind) are checked by `client.test.ts` and
  `portal/client.test.ts`; nothing else can leave the browser.
- **Tool state only from Klipper.** `rhino.ts:91-115` reads `SWAP_TOOL.current_tool` and treats the saved slot as
  "last saved" only; the toolchanger adapter treats sensor mismatch as a stop. Browser storage holds only view
  conveniences (`settings.ts`, fold states).
- **The machine enforces the rules again.** `M104`/`M109`/`SET_HEATER_TEMPERATURE` wrappers and `_RHINO_HEATER_WATCH`
  (`toolchanger.cfg:275-310`) refuse the hotend without a print head, and `G28` (`:330-349`) refuses Z homing
  without one, so a request sent straight to Moonraker meets the same gate (M2 is the one way round it).
- **The three no-confirm validators are tight.** `isTuningScript`, `isHardwareScript` (never a tool output) and
  `isScrewScript` (only Z motors Klipper has, ≤ 5 mm, Z marked unhomed first) accept exactly their builders' output.
- **The updater never gives the Portal sudo.** Root helper reads with `O_NOFOLLOW`, copies the zip before checking
  it, rejects absolute paths, `..`, backslashes and links, refuses during a job, backs up first, keeps the previous
  zip for Go back, and the GitHub path pins hosts and checks the SHA256 (`rhino_update_helper.py`,
  `update_routes.py`). Only authenticity is missing (M5).
- **The network helper is careful.** Strict regexes for every argument, password on stdin, a revert timer armed
  before the change, one sudoers line for one root-owned file (`rhino_net_helper.py`, `install.sh:310-318`).
- **Backups and restore.** Complete-or-refused archives with a manifest, restore targets normalised and checked
  against their base folder (`backup.py:369-384`), typed host name and `[mcu] serial` check for a full restore, a
  backup taken first.
- **Config edits in Studio** copy the file to `config/studio_backups/*.bak` before saving (`FileBrowser.vue:410-454`)
  and never restart by themselves; Portal edits of a pin line are backed up, read back and reverted if they don't
  parse (`service.py:461-504`); `trusted_clients` edits are parsed back, backed up and reverted if Moonraker doesn't
  come back (`trust.py`, `trust_routes.py`).
- **Generated config can't be injected.** Names go through `NAME_RE`, `MACRO_NAME_RE`, `CONTROL_NAME_RE` and notes
  through `SAFE_TEXT` (`presets.py:15-86`); `sections.py` renders from validated dicts and `parse_like_klipper`
  reads the result back.
- **Idle behaviour.** The hologram stops drawing and the camera stream pauses when the tab is hidden; a socket close
  clears the status so nothing stale shows as live (`client.ts:712-717`); prompt buttons are debounced
  (`promptBusy`).
- **Secrets.** No tokens, keys, Wi-Fi details or personal paths in either repo; `rhino-backup` is private.
